# Architecture

Read `CLAUDE.md` first.

---

## Two phases

We build in two distinct phases. Phase 1 is optional: only if Phase 0 is
fully working and there's time left.

### Phase 0 — LLM wrapper (build this first)

The app works end-to-end without any retrieval:
- Real CV parsing (extraction + LLM structuring)
- 3-call LLM analysis pipeline
- Mentor chatbot with conversation history
- Supabase Postgres for all structured data (profiles, CVs, analyses, chat)
- No vector DB, no embeddings, no chunk retrieval
- Domain knowledge the LLMs need (what a good Data Analyst CV looks like,
  what the Italian job market expects, etc.) lives as **static text inside
  the system prompts**

At the end of Phase 0 the demo is fully functional and pitchable. If Phase
1 never happens, that's fine.

### Phase 1 — Real RAG (only if Phase 0 is done with time to spare)

A retrieval layer is added on top of Phase 0:
- pgvector on Supabase
- LangChain (TS) for the retrieval pipeline
- OpenAI embeddings
- Corpus to populate: the ESCO EU competence taxonomy + synthetic job ads
  generated by LLM (exact decisions on roles, volume, metadata filtering
  are deferred to when Phase 1 actually starts)

Retrieved chunks get **injected into the same prompt context** already used
in Phase 0. None of the 4 screens change. The 3 analysis calls and the
mentor stay the same — they just receive richer context.

---

## The key architectural rule: separate context gathering from context use

This is the most important constraint for making the Phase 0 → Phase 1
transition painless.

Every LLM call (the 3 pipeline calls + each mentor turn) must receive its
context from a dedicated function that assembles it. Don't read Postgres
directly inside the function that calls the LLM. Don't build strings
ad-hoc inside route handlers.

The idea: a function like `gatherContext(...)` that returns a "prompt
context" object. In Phase 0 that function only reads from structured data
(CV, survey, previous analysis, chat history). In Phase 1 the same function
also queries pgvector and adds the relevant chunks.

**LLM call sites don't change between phases** — they receive a context
object and use it. Only what's inside the object changes.

The developer decides the exact fields of that object when writing the
code — the important thing is that the abstraction exists from day one.

---

## Two kinds of data

In Phase 0 we only have structured data on Postgres: who the user is, what
they uploaded, what they said in chat. Queried by ID, filtered with SQL,
fast and predictable.

In Phase 1 a second kind is added on pgvector: general knowledge about the
job market (role descriptions, job ads, ideal CV examples, learning
resources). Not queried by ID but by semantic similarity.

**The two kinds must never be mixed.** The user's CV is personal,
structured, always needed in full → Postgres. Job ads are thousands of
documents searched by meaning → pgvector.

In Phase 0 this distinction is invisible because the vector DB doesn't
exist yet. But the code should be written as if it did: the "context"
passed to the LLM should be treated as an object with two potential sources
(structured + retrieved), even if the second source is always empty for now.
